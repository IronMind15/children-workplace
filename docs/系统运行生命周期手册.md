# 知识岛系统 · 运行生命周期完整手册

> 适用范围：本机 / 局域网使用（Electron 未落地，当前为「Next.js production 服务 + 浏览器」形态）
> 编写依据：2026-08-18 对 `package.json`、`next.config.ts`、`lib/db.ts`、`lib/seed.ts`、`lib/ai.ts`、`.gitignore`、`app/` 目录结构逐一核对
> 目标：保证每一次都能顺利、稳定地打开和使用系统；并为后续公网分发给出风险清单与应对

---

## 一、系统运行模型（先把逻辑理清）

### 1.1 一次请求的生命

```
浏览器 ──HTTP──> Next.js 服务（默认 3000 端口）
                    │
                    ├─ Server Component 直读直写 SQLite（lib/db.ts 单连接，同步 API）
                    │       └─ data/app_data.db（DELETE journal 模式）
                    ├─ 页面首访触发 seedIfEmpty()（schema_version=6 幂等，已迁移则零开销）
                    └─ AI 功能：服务端 fetch api.deepseek.com（key 在库内 ai_config 表）
```

**三个关键事实（务必记住，所有排障都围绕它们）：**

| 事实 | 内容 | 出处 |
|---|---|---|
| 数据库文件 | **`data/app_data.db`**（`app.db`、`app.db.bak` 是旧库/备份，非当前使用） | lib/db.ts:14 |
| 构建必须 webpack | Turbopack 本机死锁，`dev`/`build` 一律 `--webpack` | package.json |
| 无 API 层、无鉴权 | 全部路由是 Server Component 直读写 DB；单用户 `default`，无登录 | `find app -name route.ts` 为 0 |
| AI 是唯一外网依赖 | DeepSeek API，key 存库内 `ai_config` 表；未配置自动回退内置题库 | lib/ai.ts |
| 数据不入库 | `.gitignore` 排除 `data/*.db*`，新环境首启自动重建空库 | .gitignore |

### 1.2 生命周期总览（7 个环节）

```
 P0 前置检查 ──> P1 启动服务 ──> P2 打开浏览器 ──> P3 使用系统
                                                  │
 P6 重启验证 <── P5 关闭服务 <── P4 关闭浏览器 <──┘
 （P6 完成后回到 P0/P1，形成循环）
```

> 每个环节统一回答：①确切命令/操作 ②前置条件与完成后状态 ③故障点 + 排查与预防
> 命令均在项目根目录 `D:\first_harness\知识岛` 下执行，Shell 为 Git Bash（Windows）。

### P0 · 前置检查（每次启动前，约 30 秒）

**① 操作（按顺序执行）：**

```bash
cd "D:\first_harness\知识岛"

# 1. 端口空闲检查（3000 无 LISTENING）
netstat -ano | grep ":3000" || echo "端口空闲"

# 2. 残留进程检查（确认无本服务残留 node 进程）
tasklist | grep -i node || echo "无 node 进程"

# 3. 数据库目录卫生（无 journal/shm 残留）
ls -la data/

# 4. 构建产物新鲜度（仅改过代码时需要关心）
cat .next/BUILD_ID 2>/dev/null && ls -l --time-style=+%Y-%m-%dT%H:%M:%S .next/BUILD_ID

# 5. 依赖完整性（首次运行/换机器时）
ls node_modules/.bin/next 2>/dev/null || npm install
```

**② 前置条件 / 完成后状态：**
- 前置：Node ≥ 22.5（`node -v` 验证，engines 要求）
- 完成后：端口空闲、无残留进程、`data/` 下只有 `app.db*` 系列（无 `-journal`/`-shm`）、`.next/BUILD_ID` 存在（首次则需先 P1 前构建）

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| 端口被占用 | 步骤 1 有 LISTENING 行 | 记录 PID → `taskkill //F //PID <pid>`（确认是旧服务再杀，勿误杀） |
| 服务未完全退出 | 步骤 2 有 node 进程 | 按 PID 精准杀，**不要** `taskkill /IM node.exe` 全杀（会殃及其他项目） |
| journal 残留 | `data/` 有 `app_data.db-journal` | 先确认无进程在写（步骤 2），残留是上次强杀的产物，lib/db.ts 启动时会自愈删除 |
| 构建产物过期 | BUILD_ID 时间戳早于源码修改 | 需先构建（见 P1 备选），否则 `next start` 会服务旧包 |

**验证方法：** 5 个检查命令全部输出符合预期；任一异常先解决再进 P1。

### P1 · 启动服务

**① 操作（production 主推，三选一）：**

```bash
# 方式 A：前台启动（调试推荐，Ctrl+C 即停）
cd "D:\first_harness\知识岛"
NODE_OPTIONS="" npx next start          # 默认 3000；换端口加 -p 3001

# 方式 B：后台启动（日常推荐，需记录 PID 以便关闭）
cd "D:\first_harness\知识岛"
nohup npx next start > next.log 2>&1 &
echo "PID=$!"

# 方式 C：改过代码后先构建再启动（两步）
cd "D:\first_harness\知识岛"
rm -rf .next                            # 仅当构建曾挂起/产物可疑时
NODE_OPTIONS="" npx next build --webpack
NODE_OPTIONS="" npx next start
```

> 开发模式（仅编码时）：`npm run dev`（内部即 `next dev --webpack`）。**切勿**裸跑 `next dev`/`next build`——Turbopack 本机死锁。

**② 前置条件 / 完成后状态：**
- 前置：P0 全部通过；`.next` 构建产物存在且新鲜（方式 C 可不要求）
- 完成后：
  - `netstat -ano | grep ":3000"` 显示 `LISTENING`
  - `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000` 返回 `200`
  - 日志出现 `Ready in ...` / `started server` 字样
  - 数据库被正确打开：`data/app_data.db` 存在，无 `-journal` 残留

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| EADDRINUSE（端口占用） | 启动即报错退出 | 回 P0 步骤 1-2 找 PID 杀掉；或改用 `-p 3001`（同时改浏览器地址） |
| 服务没起来但端口被占 | 端口有 LISTENING 但页面 404/无法访问 | 旧进程还在——按 PID 杀净再启 |
| 服务旧包（最常见隐蔽坑） | 改了代码页面无变化 | `next build` 偶发挂起（无输出、BUILD_ID 不更新）→ 启动前核对 BUILD_ID 时间戳；必要时 `rm -rf .next` 全量重建 |
| readonly 报错（errcode 8） | 页面 500，日志 SQLITE_READONLY | 先跑 `python scripts/probe_lock.py data/app_data.db`：OK=服务进程缓存了锁错误，**重启服务而非删文件**；FAIL 才找持锁进程 |
| Turbopack 死锁 | build/dev 卡死无输出 | 所有构建命令必须带 `--webpack`；已卡死则 `taskkill //F //PID` 后重试 |
| 构建时 NODE_OPTIONS 污染 | webpack OOM / 异常 | 构建与启动前一律 `NODE_OPTIONS=""` |

**验证方法：** ①端口 LISTENING ②curl 200 ③日志 Ready ④改代码场景核对 BUILD_ID 时间戳晚于源码。

### P2 · 打开浏览器

**① 操作：**

| 场景 | 地址 |
|---|---|
| 本机 | `http://localhost:3000` |
| 局域网（手机/平板同网段） | `http://192.168.31.147:3000`（dev 模式已配 `allowedDevOrigins`；production 无此限制） |
| 换了端口 | `http://localhost:<端口>` |

**② 前置条件 / 完成后状态：**
- 前置：P1 已确认端口 LISTENING
- 完成后：首页加载出「群岛」视图（默认 🏝️ 群岛，7 页分页），控制台无 500/404，Network 面板主要资源全 200

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| 页面空白 / JS 加载失败 | F12 看到 chunk 404 或报错 | 多数是服务旧包（回 P1 重建）；硬刷新 `Ctrl+F5` 排除浏览器缓存 |
| 浏览器缓存旧版 | 界面是旧样式/旧功能 | 静态资源带 hash 一般不会命中旧缓存；仍异常则硬刷新或清站点数据 |
| localStorage 残留 | 地图模式/引导开关异常（如 tutorial 不弹、地图模式不对） | `F12 → Application → Local Storage → 清除 kb:*` 键；进度本体在数据库，清 localStorage 无损 |
| 局域网打不开 | 手机访问超时/拒绝 | Windows 防火墙放行入站（node.exe / 3000 端口）；确认在同一网段；确认服务监听 `0.0.0.0`（next start 默认即可） |
| 端口混淆 | 之前用过 `-p 3001` | 以实际启动命令为准；建议固定端口避免记忆错位 |

**验证方法：** 页面渲染正常 + Network 全 200 + 群岛可翻页、可切「🗺️ 大地图」。

### P3 · 使用系统（数据写入验证）

**① 操作（正常使用即可）：**
- 登岛打小怪 → 答对净化 → 挑战 Boss → 觉醒知识守卫 → 提问 AI / 费曼小课堂 → 查看成长/错题

**底层行为（帮助判断"正常"）：**
- 首次访问任意页面触发 `seedIfEmpty()`：新库全量播种（29 元认知/精灵/Boss/性质/策略/守卫），老库按 `schema_version=6` 幂等迁移，之后每次请求零开销
- 所有页面 `force-dynamic`：每次请求实时读库，改完立即生效
- 答题/战斗结果同步写库（`internalized_meta`、`growth_log`、`mistake`、`boss_progress` 等）
- AI 提问 = 服务端 `fetch(api.deepseek.com)`：key 在 `ai_config` 表；未配置 key 时自动回退内置题库/演示模式

**② 前置条件 / 完成后状态：**
- 前置：服务正常（P1）；AI 功能需本机可访问外网 + 库内有有效 key
- 完成后：`data/app_data.db` 有数据增长（`growth_log` 新增行）；AI 面板返回小狐狸回答

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| AI 无回复（历史根因） | 面板显示"AI 无回复" | 已修复根因：推理模型 `reasoning_content` 耗尽 max_tokens → 现 max_tokens 1000/300/800 + content 兜底。若再现：查 `ai_config` 表 key 是否完好、外网可达性、配额 |
| AI 报 unconfigured | 提示未配置 | 检查 `ai_config` 表是否有行；key 失效重填（设置页） |
| 数据库 locked | 页面 500，日志 database is locked | `busy_timeout=5000` 已兜底；仍发生多为并发写冲突（dev 模式多请求），等 5s 重试或重启服务 |
| 页面 500 | 白屏/报错 | 看 `next.log`（后台模式）或终端栈；常见为 readonly（回 P1 排障）或磁盘满 |

**验证方法：**
```bash
# 页面冒烟（7 个主页面全 200）
for p in "" ask brain growth journal mistakes profile parent; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "http://localhost:3000/$p")
  echo "/$p -> $code"
done

# 数据落盘验证
curl -s http://localhost:3000/ > /dev/null
ls -l --time-style=+%H:%M:%S data/app_data.db   # 时间戳应随使用更新
```
AI 验证：面板发问一次，应收到 ≤150 字回答（或兜底内容）。

### P4 · 关闭浏览器

**① 操作：** 直接关闭标签页或浏览器窗口即可；本环节**没有**强制操作。

**② 前置条件 / 完成后状态：**
- 前置：无
- 完成后：浏览器进程退出；与服务端的 HTTP keep-alive 连接随之释放；服务端**不受影响**（端口仍 LISTENING）

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| 「连接未释放」担忧 | —— | 本系统无 SSE/WebSocket 长连接（仅 dev 模式有 HMR websocket），HTTP 短连接随进程退出即释放，无需担心 |
| 强杀浏览器 | 浏览器崩溃退出 | 数据已实时落盘（每次写都是同步事务），**不会丢进度**，无需恢复操作 |
| 页面假死但浏览器在跑 | 标签无响应 | 刷新页面即可；不影响服务端与其他用户 |

**验证方法：** 浏览器关闭后 `netstat -ano | grep ":3000"` 仍 LISTENING；服务端日志无异常。

---

### P5 · 关闭服务

**① 操作（按顺序尝试）：**

```bash
# 方式 A：前台启动的 —— 在启动终端按 Ctrl+C（优雅退出，DB 正常关闭）

# 方式 B：后台启动的 —— 用记录的 PID 优雅终止
kill <启动时记录的 PID>
sleep 2
netstat -ano | grep ":3000" || echo "端口已释放"

# 方式 C：优雅退出失败/未知 PID —— 按端口精准强杀（最后手段）
netstat -ano | grep ":3000"        # 取最后一列 PID
taskkill //F //PID <pid>
```

**② 前置条件 / 完成后状态：**
- 完成后（用命令验证）：
  - `netstat -ano | grep ":3000"` 无输出（端口释放）
  - `tasklist | grep -i node` 无本服务进程
  - `ls data/` 无 `app_data.db-journal` / `-shm` 残留

**③ 故障点与排查：**

| 故障 | 症状 | 排查与预防 |
|---|---|---|
| Ctrl+C 后端口仍被占（最典型） | 重启时报 EADDRINUSE | 根因：Windows 下 `npm run start` 是 cmd→npm→node 进程树，杀掉 npm 壳，node 子进程存活。**预防**：直接 `npx next start`（少一层壳）；强杀时按端口找 PID |
| 强杀产生 journal | `data/` 有 `-journal` 残留 | lib/db.ts 启动自愈会删除；无需手动处理（确认无进程占用后也可手动删） |
| 误杀其他项目 | 别的 node 服务中断 | 永远按端口定位 PID 再杀，禁止 `taskkill /IM node.exe` 全杀 |

**验证方法：** 端口释放 + 无 node 进程 + 无 journal 残留（三条命令逐一确认）。

### P6 · 下次重启（循环回到 P0）

**① 操作：** 完全回到 P0 → P1 → P2。唯一新增动作：**先回顾上次退出是否干净**（若 P5 验证全过，直接 P0 步骤 1-2 快速确认即可）。

**② 快速重启检查点（30 秒版）：**

```bash
netstat -ano | grep ":3000" || echo OK-端口空闲
tasklist | grep -i node || echo OK-无残留进程
ls data/ | grep -E "journal|shm" || echo OK-无残留锁文件
```

**③ 故障点与排查：** 与 P0/P1 完全同源。预防要点汇总：
1. 端口、端口、端口 —— 一切重启失败先查端口
2. 杀进程按 PID，不按名字
3. 改过代码必核对 BUILD_ID；怀疑旧包就 `rm -rf .next` 重建
4. readonly 先探针（probe_lock.py），OK 就重启服务，别删库

**验证方法：** 三连 OK + P1 的 curl 200 冒烟通过，即完成一次稳定循环。

## 三、公网部署风险与应对（多次本机验证成功之后）

> 现状事实：**无 API 层、无鉴权、单用户、AI key 明文存库内**、无 TLS、无日志落盘、无进程托管。以下按优先级排序。

### 3.1 端口暴露与安全加固（最高优先，先做这个）

| 风险 | 应对 |
|---|---|
| `next start` 裸监听 3000，公网直接可达，无 TLS，HTTP 明文 | **必须加反向代理**（nginx / caddy）：公网只开 80/443，TLS 终止，3000 仅回环监听（`127.0.0.1:3000`） |
| 云服务器安全组/防火墙未收敛 | 安全组只放行 80/443；服务器防火墙（ufw/firewalld）同样收敛；**3000 端口永不对外开放** |
| Host 头注入 / DNS rebinding | 反向代理层配置 `server_name` 白名单 + 拒绝未知 Host |
| 数据库文件可被下载 | `data/` 目录绝不能落在 web 静态根（Next 的 `/public` 才是静态根，`data/` 在进程内，正常不可下载）；部署后**实测** `https://域名/data/app_data.db` 返回 404 |
| 依赖/镜像 | 生产环境固定 `npm ci`（锁文件）+ 锁定 Node 版本 |

### 3.2 访问鉴权（上线前必须，否则任何人可读写同一份进度）

| 风险 | 应对 |
|---|---|
| 当前无登录，`default` 单用户，全页面可写 | 应用层加家长口令/邀请码（cookie/session）；或反向代理 Basic Auth 快速兜底 |
| 儿童场景敏感 | 参考 docs 已规划的「家长监管 / 防沉迷 / 内容审核」：家长控制面板、使用时长上限 |
| 鉴权绕过 | 所有 Server Component 入口统一校验（Next middleware 或 layout 校验）；不能只在个别页面加 |

### 3.3 并发与稳定性（理解瓶颈，设合理预期）

| 风险 | 应对 |
|---|---|
| `node:sqlite` 是**进程内单连接 + 同步 API**：并发请求在 DB 读写上串行化；`busy_timeout=5s` 只兜底锁等待，不提高吞吐 | 预期规模（家庭/班级，数十并发）完全够用；**避免多实例共享同一 SQLite 文件**（多进程写会锁冲突） |
| 每请求 `seedIfEmpty()` 检查 | 已优化：schema_version 命中直接返回，零开销（无需改动） |
| AI 调用为外网阻塞 | `askAi` 是 async fetch，不阻塞事件循环；但并发提问会挤占 DeepSeek 配额/限流 | 应用层做提问频率限制 + 队列；失败已有内置题库兜底 |
| 长任务/内存 | 保持单实例；监控内存与磁盘（DB 会随使用增长，单文件便于备份但也需关注膨胀） |

### 3.4 日志与监控

| 缺口 | 应对 |
|---|---|
| 当前无日志文件（后台启动才落到 `next.log`） | 用 PM2 或 systemd 托管：自动重启 + stdout 落盘 + 日志轮转 |
| 无健康检查端点 | 加 `/api/health`（顺带读一次 DB 验证可读写）；监控脚本 curl 它判断存活 |
| 无告警 | 磁盘使用率、DB 大小、进程存活、5xx 计数接入简单监控（crontab + 脚本即可起步） |
| AI 失败无记录 | 在 `growth_log` 或独立表记录 AI 调用失败类型（unconfigured/timeout/network/http），便于事后诊断 |

### 3.5 异常恢复机制

| 风险 | 应对 |
|---|---|
| 进程崩溃无人拉起 | PM2/systemd 配置 `restart=always`；启动自愈逻辑（删 journal）已在 lib/db.ts |
| 数据丢失 | `app_data.db` 单文件：**每日定时复制备份**（crontab `cp` + 保留 N 份）；升级 schema 前先备份 |
| 恢复流程 | 停服 → 用备份覆盖 `data/app_data.db` → 起服 → curl 冒烟（本手册 P1 验证）→ 定期演练一次 |
| 版本升级 | `schema_version` 幂等迁移安全；仍遵循「先备份 → 升级 → 冒烟」铁律 |

### 3.6 密钥管理（公网版必须改）

| 风险 | 应对 |
|---|---|
| DeepSeek key 明文在 `data/app_data.db` 的 `ai_config` 表；公网一旦文件泄露或备份外泄即泄露 | 生产环境改为**环境变量注入**（服务端读取，不入库），或至少：数据库文件权限 600 + 备份文件加密 + 定期轮换 key |
| 儿童隐私 | 遵守未成年人个人信息保护要求：最小化收集、家长授权；AI 对话内容不外泄到第三方日志 |

## 四、排障速查表（症状 → 根因 → 解法）

| 症状 | 根因 | 解法（按序） |
|---|---|---|
| 启动报 EADDRINUSE / 端口被占 | 上次服务未退净（npm 壳已死、node 子进程存活） | `netstat -ano \| grep ":3000"` → `taskkill //F //PID <pid>` → 重启 |
| 页面 500，SQLITE_READONLY | 服务进程缓存锁错误 / journal 残留 / 真被锁 | `python scripts/probe_lock.py data/app_data.db`：OK→重启服务；FAIL→找持锁进程 |
| 改了代码页面没变 | next build 挂起，服务着旧包 | 核对 `.next/BUILD_ID` 时间戳 → `rm -rf .next` → `NODE_OPTIONS="" npx next build --webpack` → 重启 |
| build/dev 卡死无输出 | Turbopack 死锁（本机已知问题） | 确保命令带 `--webpack`；已卡死按 PID 强杀 |
| AI 无回复 | 推理模型配额被 reasoning 耗尽（已修）；key 失效；外网断 | 查 `ai_config` 表 key → 测外网 → 面板重试；仍未解决记录 error 类型 |
| 页面空白/旧版 | 浏览器缓存 / 服务旧包 | 硬刷新 → 核对 BUILD_ID → 重建 |
| 局域网打不开 | 防火墙未放行 / 不在同网段 | 放行 node.exe 与 3000 入站；dev 模式核对 `allowedDevOrigins` |
| 重启后数据"没了" | 用的是新库（`app_data.db` 被误删/换库） | 明确当前库是 `app_data.db`；误删则从备份恢复（定期备份见 3.5） |
